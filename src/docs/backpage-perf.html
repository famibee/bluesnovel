図2 — 不可視 back ページで動き続けるもの

[trans] 後、back になったページ (110) は visibility:hidden でも DOM に残る。中で自走する 5 つのうち 4 つ（video・fx・CSS シート・プラグイン）は物理ページに固定された実体なので「可視シグナル」で止める必要があり、実際 2026-08-28 に対応済み。無限 [tsy] だけは書き先が役割相対で可視ページを追い続けるので、止める対象がそもそも無い——残るのは Stage の再描画コストだけ（図3・対照表）。

図3 — なぜ [tsy] だけ pause できないか

chgLay の page:'fore' は文字列で、store の pickPage が set() 実行時点の foreIdx で物理ページ 0/1 に解決する。つまりトゥイーンは 物理ページにもレイヤオブジェクトにも束ねられておらず、fore / back という役割に束ねられている。[trans] で foreIdx が反転すると、同じトゥイーンの書き先が新しい表ページへ乗り移る。なお [trans] 自体はレイヤをクリアしないし走行中 [tsy] も kill しない（finTrans は役割の入れ替えと新 fore → 新 back の structuredClone だけ）。[tsy] を畳むのは [clear_lay] / [er] / [stop_tsy] / 読み戻り / スクリプトジャンプ。

図4 — memo 化が飛ばすもの／飛ばさないもの

残るコストは「無限 [tsy] の set() で Stage が表裏とも再 render すること」だけ。React の既定では親が再 render すると子は props に関係なく全部呼び直される（そのあと diff して「DOM 変更なし」と分かる — が、その render 作業はもう済んでいる）。React.memo は、渡ってきた props が前回と全部 === ならその関数を呼ばずサブツリーごと再利用する。

読み解きメモ（論点）

  1. 太い流れ：(10)→(20)→(30)→(70)→(90)→ページ→レイヤ→(210)。(10)–(30) はブラウザ非依存で単体テストできる（test/*.test.ts）。
  2. 状態は全部 (70)。ただし (50) FrameMng・(60) SndMng・(190) PlgLayMng だけは例外で store の外に実体を持つ（それぞれ理由あり：iframe の same-origin / howler を積まない自前 Web Audio / DOM 側の Layer インスタンス表裏 2 個）。
  3. 逆流（イベント）：進行の自己トリガ (30)→heStage 'ev_next'→(80)→go()→(30)（DOM を挟んで疎結合）に加え、待ち合わせの完了もすべて (30) へ戻って go() を再開させる：文字送り完了 (120)→(70)→(80)→onTypingDone()、[wait_tsy]／[wt] のトゥイーン・演出完了（#onTsyEnd／#finishTrans）、[wv] の video ended（#waitVideoPlay）、[wait_fx] の FxRunner one-shot 完了（fx タイマー）、[wf]／[wb] の音声フェード完了（#onSndFadeEnd）。図1 は太い順流だけを描いている。
  4. 自走するもの（図の自己ループ）：(40) Tw の内部 rAF、(160) video デコード、(170) FxRunner の rAF、(200) プラグインの #tick。表ページで動くぶんには問題なし。(200) の #tick は (40) Tw の一種ではない — Tw は数値プロパティの補間（エンジン所有）、#tick はプラグイン自前のレンダーループ（sn_gallery 側・不透明）。エンジンが渡すのは可視シグナル setActive() だけでよい。
  5. (40) Tw が (70) を直接触らない理由：書き込み対象が安定して存在しない。音声フェードの Tw は new Tw(gn.gain) で GainNode を直接書く（生オブジェクトで寿命が音と一致）。[tsy] のレイヤは set() のたび immutable update で作り直され [trans] で入れ替わるので、掴んだ参照は 1 フレームで陳腐化 → 毎フレーム chgLay({nm, page}) で名前引きし直す。apply() がその「渡すクロージャ」そのもので、#hTw 台帳・withAlign・backlay を要するため (30) の中にしか置けない。
  6. 可視シグナルは用途ごとに別経路（図2）。(170)(160) は (90)→(130) の React prop fxActive、(150) は (90)→(110) の CSS 変数（cascade で子孫へ）＝どちらも「状態を流して下流が振る舞いを変える」形。(200) だけ (30)→(190)→setActive() の out-of-tree なのは、プラグインの実体（Three.js / Live2D）が React ツリーに居ない（(180) は空の箱 <div> だけ、中身は attachPlgBox() が命令的に append）ため prop も cascade も届かないから。いずれも 2026-08-28 に対応済み。
  7. 物理ページ固定 vs 役割相対（下表）。video / plugin / CSS シートは物理ページ index 0/1 に固定された DOM 実体で、[trans] 反転後は旧ページの実体が誰にも見られず走り続ける＝pause / setActive が必須。[tsy] は書き位置が store 経由の page:'fore'＝役割相対で、pickPage が毎フレーム今の foreIdx に解決するので可視ページへ自動追従する。だから [tsy] に可視 pause は道具として不適で、そもそも不要。
  8. [tsy] に残る作業は最適化 1 点だけ。正しさの問題ではない。page=fore の [tsy] は構造上つねに可視ページを書くので「止めるべき不可視アニメ」は無い（純粋不可視は page=back 明示 × [trans] 外というニッチのみ）。残るコストは onUpdate→chgLay→set()→ Stage が表裏とも 60fps 再描画すること。対処は (c) back ページ <div> の memo 化（putPage が非対象ページの配列参照を保つので back 側の再描画だけ確実に止まる）。(a) page=back 限定 pause は狭すぎ、(b) 作成時の物理ページへ束縛は chgLay の動的解決を変える中規模改修。
